- `db_retry.py` — `connect_with_retry` / `is_lock_conflict`. DuckDB allows one writer, and the unattended jobs contend for it: signal-watch opens ~10 connections per run, xsmom syncs thrice daily, and the web backend takes a write lock at startup and on the stats-cache refresh. Because every timer is `Persistent=true`, a resume from suspend fires several catch-ups **in the same second** rather than on their staggered schedules — that is how `buibui-xsmom-daily` died on 2026-08-11 (both timers report a last trigger of 09:27:34). Retrying at connect time covers whichever job holds the lock; a fix aimed at one holder does not. Budget ~52s over 6 attempts, sized to outlast a full signal-watch run. **Only `Conflicting lock` is retried** — DuckDB raises a bare `IOException` for every I/O failure, so a bad path must still fail immediately rather than a minute later. Wired into ALL THREE scheduled-job modules — `analytics_runner`, `recalibrate_runner` and `signal_runner` (11 call sites) — none of which connects directly; `tests/test_db_retry_wiring.py` gates that structurally rather than behaviourally, because the failure mode is someone adding an 11th direct `duckdb.connect` months from now. ⚠ **`is_lock_conflict` has a SECOND consumer since ST70(a)** — `signal_runner._sync_watched_series` narrows the per-symbol `sync` failure the same way. That site caught `IOException` bare and logged *"will retry"*, which nothing did: both production callers run `--once` (`deploy/run-signal.sh`, `.github/workflows/signal-watch.yaml`), so the cycle went on to scan, alert, write `signal_alert_outcomes` and advance the CooldownStore watermark against bars it had just failed to refresh — permanent under `--catch-up`. The lock case is also the least likely to reach it, since `conn` came from `connect_with_retry` and the process already holds the write lock.

- `audit_guard.py` — P0a-2 commit gate (sub-PR 2): `evaluate_audit_cells(cells, *, bar=0.05, alpha=0.05, min_n=30, ...)` → list of `CellVerdict` (`ENABLE` / `DISABLE` / `CONCENTRATE` / `INSUFFICIENT`). Replaces the audit tools' crude ±0.05R bar with two gates that BOTH must hold: a **cluster bootstrap CI** (`cluster_bootstrap_ci`) on the suppressed slice's mean R clearing the ±bar, AND a **Holm multiple-testing-adjusted p-value** (`haircut_sharpe` over the tested-cell family) < alpha, formed on `n_eff = n / DEFF` and never the trade count. **⚠ ST80 (2026-08-25): `AuditCell.cluster_key` is REQUIRED**, one entry per `supp_r` row, positioned before the defaulted `kept_r` so mypy refuses a call site that omits it — it refused ten across nine files. A mismatched length **fails closed** to INSUFFICIENT and leaves the Holm family, rather than reverting to per-trade resampling: an unmeasurable panel and an uncorrelated one must not both read as a deflator of 1.0. `CellVerdict` reports `n_clusters` + `design_effect`, because a deflator applied silently is indistinguishable from one that was forgotten. The old `block_bootstrap_ci` could not reach the dependence for TWO reasons — same-day cross-symbol rows are not adjacent, and **no trade query feeding a cell carries an `ORDER BY`**, so its adjacency was DuckDB storage order. `boot_method` is gone (`weekly_path` was the one caller). Measured: trade-weighted DEFF 4.991, 70 of 125 cells significant → 52, and `powered_null` 0 of 125 before AND after, so no filed verdict moved. Verdict `docs/audits/2026-08-25-st80-audit-guard-cluster-key.md`. Below-`min_n` cells are `INSUFFICIENT` and excluded from the haircut family. **`CellVerdict.powered_null` (added 2026-08-13) is the definition of a powered null FOR A CELL VERDICT — `ci_lo > -bar and ci_hi < bar`, i.e. the CI RULED OUT an effect at the bar in both directions.** Consumers must read that field and must never re-derive power from `n >= min_n`: a sample-size floor cannot tell "smaller than the bar" from "the CI is 5x the bar", and four modules made exactly that inference until it was corrected (H14's 10 published NO-EDGE cells all became INSUFFICIENT). ⚠ **It is NOT the only shape — this entry said "the ONE definition" until ST27 (2026-08-14) and that was wrong.** A best-of-k **selection** construct has only a one-sided claim on offer (*no arm beats baseline*), so it needs `sl_horizon.negative_claim_licensed` — `all arms' ci_hi < bar` — and dropping `powered_null` in there would demand containment on a lower bound that is irrelevant to the claim. **Match the predicate to the claim's shape; two-sided is not a safe default.** ST27 also shows the defect family is not one mistake: four sites inferred power from a sample-size floor, the fifth from *failure to clear a threshold* — same shape, different tell, so a grep for `min_n` finds only four of five. Pure (consumes `research_guards`, no DB/IO); mirrors `sweep_guard.py`'s verdict shape. Consumed by `tools/gate_audit.py` + `tools/adr_threshold_audit.py`. - `eras.py` — **era boundaries: the dated system-rule changes a performance sample must not straddle** (SoT ST17 / Stream B "playbook era versioning"). Two sources. **git-derived** from the history of behaviour-changing paths (`BACKTEST_PATHS` = the regression trigger set minus fixtures/lockfile; `LEDGER_PATHS` = the signal path **plus `analytics/strategies`**) — drift-proof because the commit IS the record, so nobody has to remember to file a config change. **⚠ `LEDGER_PATHS` excluded the detectors until 2026-08-18, on the reasoning that a detector change only moves backtest rows.** The `bos` causality fix is the counterexample that closed it: re-stamping a signal from the swing bar to its confirmation bar changed the ledger's `candle_ts_ms`, changed the alert's quoted entry price (the live alert quotes the close of the STAMPED bar, so it had been quoting one five bars stale) and cut `bos` alert volume by ~80% once the gates began evaluating at the decision bar. All three are ledger CONTENT, and none of them would have opened a ledger era. **A detector edit is a ledger event whenever it changes what is emitted or when.** Cost of the widening, measured over the ledger's 146-day span: 4 extra boundaries against 46, so the fragmentation is ~9%. **declared** in `config/eras.toml` for what git cannot see: a DB prune, a re-run that rewrote stored rows, a data gap that made a window unrepresentative. `load_boundaries` / `straddled` / `split_by_era` / `straddle_report`, plus `NON_BEHAVIOUR_TYPES` (`docs`/`test`/`ci`/`style` are not boundaries; `chore`/`build`/`refactor` deliberately ARE, since a dep bump, a config tidy and a file move have each moved goldens here). Boundaries carry a **`scope`** (`backtest` / `ledger` / `ratings`) so a consumer segments only on what applies to its rows — pooling scopes made the 08-13 ratings prune read as the opener of the largest *backtest* sub-sample. **`ratings` is DECLARED-ONLY, and that is a decision rather than the gap it looks like** — `recalibrate_lib.py` is in neither path set, so nothing git-derived marks a star change. The commit is not the event: stored rows only move when somebody RUNS `recalibrate --apply`, which can be weeks later or never (#662 merged 2026-08-19 and moved nothing until the apply four commits afterwards), so a git-derived ratings boundary would date the era to the merge and fire for a recalibration nobody ran. Pinned by `tests/test_eras.py::test_ratings_scope_is_declared_only_and_never_asks_git`, whose injected runner raises if the scope shells out. ⚠ **The corollary is that an undeclared apply is invisible**: the 2026-08-18 post-causality-fix recalibrate (stored ★≥4 **47 → 43**) was recorded nowhere and was recoverable only from the daily backups either side of it, which rotate. **⚠ EVERY FAILURE RAISES** — a missing registry, a malformed entry, a failed git call. Returning `[]` would report "this sample straddles nothing", a false all-clear of exactly the shape the powered-null family had. **⚠ THE ERA KEY IS NOT THE SAME COLUMN IN EVERY TABLE, and this is the one way to misuse the module.** A backtest row's `entry_time` is *simulated market time* — a run executed today over 2025-09 bars stamps 2025-09 on rows produced by today's code, and every trade in one run shares one code version — so the key there is **`backtest_runs.run_at_ms`**; for the live ledger it is the **fire time**. Both are integer ms and neither name says which, the `bar`-units trap in a new location; keying the decay review on `entry_time` reported 64% of its sample as pre-dating the first boundary, which only meant the OHLCV is older than the repo. Consumed by `tools/decay_review.py` and `analytics/recalibrate_runner.py` (backtest scope, both through `recalibrate_lib.sample_run_times`, so the decay review and the ★ table date one pool; recalibrate prints **NOT RUN** on a loader failure rather than raising, so a git hiccup cannot block `make db-update`) and `portfolio/report.py` + `cli/portfolio.py` (ledger scope — `format_report(..., boundaries=None)` prints **NOT RUN** rather than nothing, because a silently-skipped check reads exactly like a passed one). First readings, both new information: the decay review's rated pool straddles **56** boundaries with only **55%** of its runs post-dating the newest, and the P1 replay's 322 sized trades straddle **46** with a largest single-era sub-sample of **32%**.
