- `trade/` — execution layer (P3 XS-solo live wiring, sub-project #3 slice 2 + #4). Turns the read-only `analytics/xsmom/live.py::TargetBook` into overlay-gated Binance Futures orders; consumes the XS book while keeping `analytics/xsmom/` pure/read-only. `routing.py` (PURE: `build_order_plan` — `TargetBook` + current positions + mark prices + exchange filters → `OrderPlan`; Δqty with LOT_SIZE rounding — the helper itself now lives at `portfolio/sizing.py::round_down_to_step`, shared with the F2 card post-pass so router and card round identically rather than through two copies that can drift. **That helper is deliberately not a plain `floor(q/step)*step`** — it SNAPS before it floors, because the naive form is float-fragile (`0.29 / 0.01` computes as `28.999999999999996`, losing a full lot step on a mathematically exact multiple) and its tolerance is capped below a half step on purpose, so it stays fail-safe rather than rounding a genuine sub-step remainder UP past an exchange filter. Test by ENUMERATING the input class, never by spot-checking. Rationale also rides the `sizing-round-down` context-guard card (`.claude/hooks/context-map.json`); this router is the call site that made it matter, because `delta_qty = target_qty - current` is a difference of two step multiples and so is an exact multiple *every* time, the one input class the naive form shaves — no-trade band + min-notional/min-qty skips, `reduce_only` on trims/closes but not intended flips. `order_type` is `MARKET` if `reduce_only` else `LIMIT` — maker on risk-increasing legs, taker on risk-reducing ones, BY DESIGN, so do NOT "finish the job" and make closes maker: an unfilled OPEN is bounded opportunity cost the next daily rebalance re-plans, while an unfilled CLOSE is open directional risk the book has already decided to shed. Also carried by the `xs-execution` card. `ExchangeFilters` gained `price_tick` from the exchange's `PRICE_FILTER`, used to price the LIMIT leg). `overlay.py` (PURE fail-closed `evaluate_overlay` — `RiskLimits` six independent guardrails: kill-switch, drawdown halt, gross-leverage cap, per-instrument notional cap, per-run turnover guard, data-staleness guard; any breach blocks the whole plan). `binance_futures.py` (injectable `BinanceFuturesAdapter` over `python-binance` Client; reads positions/equity/filters/marks/book-tops (`get_book_tops`)/open-order symbols (`get_open_order_symbols`); `submit(intent, price=None)` sends a post-only LIMIT (`timeInForce="GTX"`) or a MARKET order per `intent.order_type` — `submit_market` no longer exists; `cancel_open_orders` per symbol; sets one-way/cross/leverage; `mode` ∈ {`dry_run` no-op-writes, `testnet`, `live`}; hedge-mode → hard abort). `xsmom_executor.py` (orchestrator `run_once` — state → `replay_targets(capital=live-equity, now=clock)` → cancel stale managed resting orders (before the positions read planning uses, and before `evaluate_overlay` — a kill-switched or drawdown-halted run still clears its own resting orders; a correctness precondition of the fire-and-forget daily cadence, not tidy-up — a resting order is not a position, so yesterday's unfilled limit would otherwise sit on the book while today's plan submits a second order on top of it, an overshoot where both orders are individually correct and neither appears in `get_positions()`; also carried by the `xs-execution` card) → plan → overlay → submit at the book touch (LIMIT legs priced via `round_to_tick`) with per-order isolation; current gross from positions×marks with a `None`→steady-state-cap fail-safe when a held position's mark is missing; gitignored JSON state file = peak-equity high-water mark + kill-switch + last-run). Driver `tools/xsmom_execute.py` (`make buibui-xsmom-execute`): **dry-run default** (prints the order plan, submits nothing), `--mode testnet` validates the full write path at zero capital risk, `--mode live` double-gated by `--i-understand-live` + `BINANCE_ALLOW_LIVE=1` (not exercised yet — the mainnet flip is a later supervised slice); overlay defaults recalibrated to the real book envelope: `--vol-target` (0.20 validated; deploy first live cycles at 0.10), `--max-gross-leverage` 4.5, `--min-active-positions` 15 breadth guard (aborts on a thin/degenerate cross-section), `--capital` (size the book off a fixed capital instead of live account equity — threads into `run_once(capital_override=)`; for a capital-matched testnet vs real-account A/B, since position discretization is capital-dependent; omit for live = real equity; default unset is byte-identical. **A pinned run must NEVER move `peak_equity`** — it is a hypothetical and the ratchet is permanent, so a throwaway `--capital` would mutate a safety control: measured 2026-08-06, one `--capital 5000` against a 1201.33 account left peak 5000.00 / floor 3750.00 standing, which halts the book even if the account triples. **That exact poisoning then sat on disk for 14 days — the ratchet fix stops NEW poisoning and heals nothing already written — and was corrected 2026-08-20 to peak 2350.80 / floor 1763.10.** `--set-peak <value> --peak-reason "<why>"` is how: it un-writes a mark that was never real and records from/to/reason/ts into `last_run.peak_correction`, because a hand-edit repeats the original incident's real defect (that one is undiagnosable after the fact — the state file keeps only `last_run` and the invocation was never recoverable). It is **ONE-WAY on purpose**: raising is the ratchet's own job from live equity, so a CLI that could raise the mark is this same footgun rebuilt by hand; it also refuses a non-positive peak, which would put the floor at 0 and read as corrected while the breaker is OFF. ⚠ **A correction is not a resume** — it never lifts a halt the corrected floor still justifies, and re-basing down to CURRENT equity would clear the halt by erasing a real drawdown. ⚠ **The breaker compares an equity LEVEL against the mark, so a capital WITHDRAWAL is indistinguishable from a trading loss and permanently tightens it** — under sustained withdrawals the honest posture is to stay halted and re-base once at capital stability, not to let the mark drift. The pinned equity IS still compared against the existing peak, so the halt itself still applies, and `last_run.capital_override` records the pin because `last_run` keeps only the last run — without it a poisoned peak is undiagnosable. A/B runs deliberately share the ONE state file: `kill_switch` lives there, and a kill switch that skipped pinned runs would be a worse hole), auto-detected cold-start turnover allowance (lets the full book establish on day 1 without tripping the steady-state churn guard). **Daily workflow:** `make buibui-universe-sync` (`analytics sync --universe --timeframes 1h 4h 1d 1w` since 2026-08-23 — the XS book runs on 1d only, which `analytics sync`'s default `1h 4h` never refreshes, silently degenerating the book to majors-only; ⚠ **the target covers all four timeframes rather than just 1d because NOTHING ELSE refreshes the universe's 1h/4h/1w** — when it named 1d alone, 22 of 25 symbols sat frozen 17.9d on 1h, 61.2d on 4h and 76.2d on 1w with every check green, ST61a. ⚠ **But this target is HAND-RUN: nothing schedules it.** The scheduled universe sync is `deploy/run-xsmom.sh`, and ST61a fixed only the target here, so that script kept `--timeframes 1d` and the 1h/4h/1w gaps re-opened at the rate they had closed — measured 4 bars behind on 1h within a day, caught by the freshness leg ST61a itself added. **Coverage is the UNION of the callers**, which is why `tests/test_ohlcv_freshness.py::TestUniverseSyncCoverage` now pins every caller and fails when an unlisted one appears, ST61b) then `make buibui-xsmom-daily` (universe sync + executor dry-run in one command). - `deploy/` — 24/7 VPS deploy kit (systemd timers, **not** Docker; design `docs/superpowers/specs/2026-06-25-vps-deployment-design.md`, runbook `deploy/README.md`). Two timers replace the unreliable GitHub Actions cron — `buibui-signal-watch` (every 15 min, `signal watch --once --telegram --catch-up`, Binance-direct) + `buibui-xsmom` (daily 00:10 UTC, universe sync 1h/4h/1d/1w → XS executor); `Persistent=true` reruns a job missed during downtime/reboot (the exact GHA silent-non-trigger failure mode). `deploy/systemd/user/` holds the **user-scope laptop variants — the deployment actually live today**, the VPS being deferred. **`tests/test_systemd_units.py` gates them in `make test` (2026-08-15)**: no `[Unit]`-only directive under `[Service]` (the wifey fork shipped an inert `OnFailure=` that way — systemd logs `Unknown key ... ignoring` and starts the unit anyway, so `systemctl start` looks healthy while the only failure signal does nothing), `OnFailure` must name a committed unit, and every hardcoded in-repo path must resolve *including inside `ExecStart`'s arguments*, since the wrapper form puts the real script after `--`. It parses the units itself rather than calling `systemd-analyze`, because a test that skips when its tool is absent is green without having run. Replaced a `deploy/README.md` sentence that stated the same rule correctly for months and was never executed. **Five timers as of 2026-08-07j** (`buibui-backup-offsite` and `buibui-daily-check` joined the three below), and the schedules encode an asymmetry worth knowing: `buibui-signal-watch` (every 15 min) must be punctual because a missed candle is *permanent* evidence loss (the N8 watermark drags past it), whereas `buibui-xsmom-daily` (00:20/02:20/06:20 UTC, universe sync 1h/4h/1d/1w + executor dry-run) and `buibui-backup` (07:40/12:40 UTC) lose **nothing** by running late — the sync is incremental and the snapshot is a point-in-time copy — so those fire repeatedly and cheaply instead of once precisely, which is what covers a laptop that wakes with no wifi. Every non-signal-watch schedule avoids `:01/:16/:31/:46`, where signal-watch holds an exclusive DuckDB lock that on 1.5.5 refuses a second *process* even read-only. They add `--catch-up` (a laptop *creates* gaps, so without it a suspend costs ledger evidence rather than merely a late scan) — **and note the live units carry that flag in `ExecStart` directly, bypassing `run-signal.sh` entirely, which is why that script sat without it until 2026-08-07i: the omission was real but latent, reachable only on the VPS path nothing uses yet. Both now agree.** They fire at `*:01/15`, pin an explicit `PATH` (user units get a minimal one that cannot find linuxbrew's `poetry`, which `run-job.sh` needs on its *failure* path — so the alert about a broken run would itself break) and a `SyslogIdentifier` (else journald tags lines with the executable name and `journalctl --user -u` returns nothing), and **deliberately omit `network-online.target`**: that target does not exist in the systemd user manager at all, and even in system scope it is a boot-time barrier that stays active across suspend and never re-arms on resume — so the committed VPS units carry the same latent race and are immune only because a VPS never suspends. `run-job.sh` wraps each job with a bounded resolver-readiness gate, then a healthchecks.io dead-man's-switch + Telegram-on-fail; the gate exists because `Persistent=true` fires the missed run the *instant* the user manager resumes, and on 2026-08-06 an ~18s window in which nothing resolved killed all three network legs at once (the `/start` ping, the job on a DNS `NameResolutionError`, and the `/fail` ping — so healthchecks saw NO ping rather than a failed one). It sits ahead of the pings, where a unit-level dependency never reached, and is bounded + outcome-preserving (`NET_WAIT_SECS` 60 / `NET_WAIT_INTERVAL` 2 / `NET_WAIT_HOSTS` `api.telegram.org`, first host to resolve wins): a genuine outage still fails exactly as before, just later — the gate changes only TIMING, never the exit code, so it cannot mask a real network failure; It **exits 1 while the remote env var is unset**, deliberately: an enabled-but-unconfigured timer must complain daily rather than look green while nothing is copied, since `rclone config` is interactive and cannot be scripted. It runs `sync`, so remote retention tracks local retention — and therefore **mirrors deletions**, which is why it refuses to run when no `MANIFEST.json` exists under the backup root. Syncing an empty tree would delete the only remote copy, turning a local bug into total loss; that guard is proven by injection, not by inspection, and must not be removed. **2026-08-15 adds the mirror-image pair, guarding the DESTINATION rather than the source**, because the remote may share a drive with data this repo does not own: it rejects a remote with no path component (a bare `remote:` IS the whole drive) and rejects a destination holding entries the local root does not have — or one it cannot list at all, since a failed `lsf` lists nothing (only rc 3, directory not found, counts as empty; ST146) — the allowed set derived from the local root so a new snapshot tier is not read as an intruder. ⚠ **That second check compares TOP-LEVEL entries ONLY and therefore does NOT protect against a SIBLING REPO** — measured 2026-08-15 on a dry-run, a wifey-shaped root aimed at this repo's destination passed the guard and emitted `Skipped delete` over real snapshots, because both trees are `daily/` + `weekly/`. It catches an unrelated folder; it cannot tell a same-shaped sibling from our own data. **Two repos on one drive is a CONFINEMENT question, not a guard question: each needs its own remote with its own `root_folder_id`**, which makes the collision unreachable rather than detectable — a sibling *path* under one shared root leaves operator care as the only control, since every path on a pinned remote resolves inside the same folder.
